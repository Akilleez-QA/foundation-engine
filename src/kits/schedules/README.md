# kits/schedules

Optional authored **day-cycle schedules** for actors: time windows on the game clock that name an anchor (a
creator location id) and an activity, with optional travel segments, weekday patterns and conditional variants.
Pure helpers imported from `@kits/schedules`: no system, clock, mover, save data or registration is installed.
Time is an input, normally the core `GameClock.ut`.

```ts
import { defineSchedule, defineScheduleCalendar, schedulePlacement, scheduleCatchUp } from '@kits/schedules';
const calendar = defineScheduleCalendar({ dayLength: 1440, epoch: 0, cycleDays: 7 }); // 24 game minutes a day
const baker = defineSchedule(calendar, {
  id: 'baker',
  idle: { id: 'home', anchor: 'house', activity: 'rest' },           // uncovered time, days no variant owns
  variants: [                                                       // first matching variant owns the day
    { id: 'festival', when: ['festival'], windows: [{ id: 'parade', start: 600, end: 840, anchor: 'square', activity: 'dance' }] },
    { id: 'workday', days: [0, 1, 2, 3, 4], unless: ['sick'], windows: [
      { id: 'commute', start: 360, end: 420, anchor: 'bakery', activity: 'walk', from: 'house' }, // travel
      { id: 'bake', start: 420, end: 720, anchor: 'bakery', activity: 'bake' },
    ] },
  ],
});
const flags = (f: string) => save.get().flags.includes(f);           // read once per evaluation
const p = schedulePlacement(baker, clock.ut, flags);                 // entry, anchor, activity, progress, windowEnd
clock.schedule(p.windowEnd, reevaluate);                             // wake at the next change, not per frame
// After a load, sleep or fast-forward: side effects for skipped windows, then place at the exact current entry.
const r = scheduleCatchUp(baker, lastUt, clock.ut, flags, { maxTransitions: 32 });
for (const t of r.transitions) applySkipped(t);                      // in time order; r.truncated if more happened
teleport(actor, r.final);
```

| Contract | Definition |
|---|---|
| Creator-owned semantics | Day length and time unit, the pattern length, what an anchor and an activity mean, where an anchor is, how an actor moves (navigation, itinerary, teleport), which flags exist and what they read, side effects of skipped windows, persistence of flags and of the actor's last-applied time |
| Inputs | A calendar (`dayLength` 1..1e9, `epoch` finite, `cycleDays` 1..366). A schedule: an idle entry and up to 32 variants in priority order, each with optional `days` (weekdays `0..cycleDays-1`), `when` / `unless` flag lists, an optional own idle entry and up to 256 windows (1,024 per schedule). Windows are half-open `[start, end)` within `0..dayLength`, never overlapping inside a variant (touching is fine). Optional `from` makes a window a travel segment. Ids are unique across the schedule; text is 1-128 characters; at most 32 distinct flags. Schedules must come from `defineSchedule` (placement, catch-up and the roster refuse hand-built records with `TypeError`) |
| Flags | A real `Set` of true flags or a predicate returning a boolean, validated on every call even when the schedule reads no flags. Times are validated first; each mentioned flag is then read exactly once. A `Proxy` around a `Set` is not a valid `Set` receiver and throws `TypeError`: wrap other sources in a predicate |
| Outputs | `schedulePlacement` returns a frozen placement: day index, weekday, time of day, owning variant (or null), entry (anchor, activity, `from`), `idle`, `travel`, `windowStart <= time < windowEnd` on the timeline (idle time is clipped to the current day) and `progress` in [0, 1). `windowEnd` is strictly later than `time`, so waking at it always makes progress. `scheduleCatchUp(from, to)` returns occupant changes with `from < at <= to` in time order, `truncated`, `rewound`, the exact `final` placement at `to` and `daysVisited`; for every reported change `schedulePlacement(at).entry` is the reported entry. `scheduleItineraryOrder` turns a placement into plain order data for `@kits/itinerary` with an absolute deadline `ceil(windowEnd)`. `createScheduleRoster` maps actor ids to schedules with `actors()` and an anchor index `actorsMentioning(anchor)` |
| Transition rule | A change is reported at every window start (each day it occurs), wherever idle time begins after a window, and at midnight when the idle entry itself changes. Idle time crossing midnight under the same idle entry is one occupancy. A whole-day window, or an activity authored as two windows across midnight, reports a change at every midnight even though the anchor is the same; consumers that only move actors can compare anchors |
| Time resolution | Every boundary is derived from one expression on the timeline: day `d` spans `[epoch + d * dayLength, epoch + (d + 1) * dayLength)`, a window is `[dayStart + start, dayStart + end)` and an end at `dayLength` is the next day's start. A time is refused (`RangeError`) when its float spacing could merge the schedule's shortest segment (`schedule.shortestSegment`, the shortest window, gap or day): roughly, segments must be at least 8 units in the last place of `max(abs(time), abs(epoch)) + 2 * dayLength`. Second-scale segments resolve up to about 1e15; with `GameClock.ut` near the present (about 2e9 seconds) segments down to about 2 microseconds resolve. A schedule whose shortest segment cannot be resolved even near its epoch (magnitude `abs(epoch) + 2 * dayLength`) is refused at definition. Also `abs(time - epoch) <= 1e15` |
| Owner | The caller. Definitions are frozen data; the roster is a bounded table the caller creates and disposes. Nothing borrows the clock, the scheduler or a save section |
| Bounds | Placement: O(variants + log windows) after reading at most 32 flags into a bit mask; one frozen record. Catch-up: flags read once, weekday owners and the next changing weekday resolved once (O(cycleDays x variants)); days without a change are jumped over, so work is O(cycleDays x variants + log windows + maxTransitions) with `maxTransitions` default 64, max 4,096. Each result reports `daysVisited`, a deterministic work count of at most `transitions.length + 2`; the tests assert it instead of wall-clock time. A local run of the worst case in the tests (366-day pattern with one changing day, 4,096 transitions, a 1.8e15 span) took about 2 ms (Node, desktop; an order of magnitude only, not asserted). Roster: `maxActors` (1..1,048,576); `actors()` and `actorsMentioning()` allocate a sorted copy |
| Overload | Catch-up beyond `maxTransitions`: `truncated: true`, later changes unreported, `final` still exact. Full roster: `assign` returns `saturated` and changes nothing |
| Cancellation | Synchronous only. Flags are read once per call: if they changed during a skipped span, split the catch-up at the change. A rewind (`to < from`, an earlier save) reports nothing and returns `rewound` with the placement at `to`. Roster `dispose()` is terminal |
| Failure and recovery | Malformed calendars and schedules (overlaps, bad bounds, unknown weekdays, duplicate ids, too many entries or flags) throw `RangeError` before anything is returned. Non-finite, out-of-span or unresolvable times throw `RangeError`; a malformed flag source, a non-boolean flag or a foreign schedule throws `TypeError`. Placement is derived from time, so after a reload re-evaluate at the restored UT; there is no state to repair |
| Composition | **Clock**: the core `GameClock` (`src/core/clock.ts`) is the time owner; pass `clock.ut` and wake with `clock.schedule(p.windowEnd, ...)`. The clock never jumps UT itself; loads (`driver.restore`) and creator fast-forwards are where `scheduleCatchUp` belongs. **Itinerary**: `scheduleItineraryOrder` produces `{tag, destination: {id: anchor, generation}, value: deadline}` for `Itinerary.edit`; pass the itinerary's `maxTextLength` to refuse an anchor it would reject. For idle time the deadline is the end of today's gap: reissue at the next wake. The itinerary controller and the creator's movement adapter own arrival. **Region activation**: two paths are needed. When a region wakes, find candidates with `actorsMentioning(anchor)` for the anchors in it and evaluate each (one lookup). Region activation never reports a region that is already active, so the caller must also keep a `windowEnd` wake per dormant actor (`actors()` enumerates them) and spawn the actor when its new anchor lies in an active region. A travelling dormant actor is only checked at its wakes; poll it more often if mid-route entry into an active region matters. **Population**: not used; a placement is derived from time, so no placement memory is needed |
| Evidence | `schedule.test.ts` (13 tests): definition refusals, placement, variant priority and once-per-call flag reads, flag-source validation order, transition ordering and idle merging, truncation, bounded long skips, a 300-schedule integer brute-force comparison, a 400-schedule decimal fuzz (day lengths, epochs and bounds; near zero and near 1e15) comparing catch-up with a wake-at-`windowEnd` sequence and asserting strict progress, resolution refusals (at evaluation and at definition), the worst case bounded by `daysVisited`, roster bounds/enumeration/foreign schedules and the itinerary helper. `consumers.test.ts` (5 tests): a real `createClock` waking at `windowEnd` and catching up after `driver.restore`; the review's non-dyadic repro on the real clock terminating; a real `createItinerary` running one order per scheduled anchor; a real `createRegionActivation` waking a region with anchor-index candidates; a region that stays active receiving a dormant actor through a clock wake |
| Review | An independent review of the first candidate found: float boundaries computed differently by placement and catch-up (a wake loop at `windowEnd` and disagreeing transitions; critical), an overstated region-activation composition (no enumeration, already-active regions), hand-built frozen schedules accepted, slow worst-case catch-up (about 187 ms), a wrong placement complexity claim, undocumented midnight transitions, flag-source validation gaps and a stale itinerary deadline. All were fixed or documented with the regression tests above. A re-review was clean; its two low notes were applied: refusing an unresolvable segment at definition with a clearer message, and replacing wall-clock test assertions with the deterministic `daysVisited` count |
| Limits | No pathing between anchors (travel `progress` is a time fraction; positions are the creator's). Flags constant across one catch-up. Windows do not cross midnight. Calendar patterns repeat every `cycleDays`; one-off dates are flags. No persistence, no network authority. Headless tests only; no browser, template or physical-device evidence |
