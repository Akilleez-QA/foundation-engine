# Dimensional inventory candidates

Creator requirement: dynamically build storage and machines, carry materials by vehicle and process multiple product/waste streams without a second stock authority. Existing inventory ledger/checkpoint APIs retain their behavior. This optional pure reducer addresses dynamic container definitions and simultaneous dimensional limits; it is not a replacement persistence service.

`parseDimensionalStock` validates/copies saved version-1 stock. `prepareStockChange` returns a complete candidate or an explicit failure. Neither retains or modifies the caller's state. The composed world envelope is the only accepted owner; it supplies command revision/receipts, reservations, deposit conservation, recipe authorization, construction bills, retained-reference claims and durable publication. An uncommitted candidate supplies no goods. Calling the reducer is not acceptance, idempotent command dispatch or cross-tab compare-and-swap.

Every immutable batch defines integer quantity units, milligrams and microlitres per unit, material phase and authored properties. A gram-based bulk batch and count-based finished item can coexist without treating a bolt count as kilograms. Volume is authored packing volume at the modeled condition; this is not a gas equation of state. Reject unsafe arithmetic rather than silently rounding. BigInt intermediates make product/capacity checks exact; public serialized values remain safe integer numbers.

Changes may add or resize storage, introduce immutable batch definitions, consume and produce several streams, evacuate and remove storage. All consumption precedes production, so an empty container cannot borrow its proposed outputs to satisfy an input. Capacity is checked on the final candidate for mass, volume and admitted phases. Failed admission changes no input, output, batch definition or container. Reusing a batch ID with different metadata fails. Opposing structural changes to the same container within one operation are rejected.

The caller configures maximum containers, batches, positions, total operation entries and properties per batch. Overload returns `limit`; other failures distinguish invalid data, unknown identities, identity conflicts, insufficient stock, occupied removal, phase mismatch and capacity. Parsing corrupt persisted state throws for the enclosing save parser to quarantine/recover. Caller-provided executable accessors are not a sandbox; persisted JSON is the normal boundary.

Preparation is synchronous and has no timer, renderer, cache or storage owner. Drop an unaccepted candidate on cancellation. On failed persistence retain the candidate in the enclosing transaction ticket; do not expose its goods and do not rerun random generation. Removing a container here proves only that its stock is empty; the composed owner must additionally reject live occupants, reservations, jobs and external claims. Retiring material definitions similarly belongs to the composition/reference-claim policy and is not implemented by this reducer.

Evidence: dimensional.test.ts covers transfers and caller isolation, dynamic storage with atomic rollback, multiple outputs/waste destination, final-state capacity, overspending, phase and identity errors, safe arithmetic, storage evacuation, bounded admission, corrupt restore, sparse arrays and special identifiers. These unit tests do not prove a composed production owner, an installed-package consumer, browser acceptance or physical-device performance. Full engine gate and consumer integration remain pending for this candidate.
