# Objective workbench

An optional desktop authoring diagnostic, opened at `tools/objective-workbench/index.html` with the development server. It uses the existing authored document, edit session, staged objectives, inventory, capability, SaveStore and reading-sheet frameworks. The tool selects finite sample rules; creators can replace them.

The unobstructed scene shows one block per **accepted consequence unit**. Open the workbench to edit a visual directed graph using native fields. Apply fields creates a local draft; Validate starts an isolated provisional run. Graph commit, undo and redo affect only the authored document. Save graph persists that section. A separate explicit adoption pins a complete committed graph and its terminal outcomes for two fresh runtime consumers; prior accepted consequences remain. New adoptions can intentionally earn again.

Each sample stage exposes its first requirement and its existing choice rows. Stage IDs and edges are explicit: removing or renaming a stage does not silently repair references. Invalid dangling edges, cycles, outcomes or bounds are refused at validation. This is a focused editor, not a complete editor for every possible staged-objective definition.

The runtime shares one finite source between two consumers. Cancel or release one without granting its retained callback authority over the survivor. Work completion first prepares a durable progress candidate; acknowledge it explicitly, then reconcile the retained fact for another recipient if needed. Release remaining work and reset the completed generation before supplying a distinct later-stage event.

Terminal choice, inventory award, capability provenance and receipt share one runtime envelope. The sample capacity is eight units, initially occupied by an explicit removable blocker. Failed storage writes retain the previous accepted scene. Retry writes the exact pending candidate; only acknowledgment publishes its consequences and closes the sheet so the scene can render. Reload restores durable state, including a candidate that reached storage before acknowledgment. An unsaved candidate can be lost on reload. Graph and runtime are independent sections with **no cross-section atomicity**. The sample passes one shared `saveBuild` value to its runtime controller and SaveStore; the exact complete envelope (version, build metadata and data) must fit the existing storage bound before a pending write is admitted. The sample configures no legacy envelope metadata. Key-specific guards detect observed external replacement/deletion, but are not distributed compare-and-swap or multiplayer authority. Corrupt/newer data blocks the affected owner rather than silently replacing accepted data.

Bounds: 64 stages, 64 requirements per stage, 16 choices per stage, 64 events per stage, 16 retained adoptions, 64 accepted runtime receipts, two related consumers and one source listener. Graph/document limits and controller refusal behavior are enforced by their owners. The native editor adds only stages up to its configured cap. Every runtime command has a fresh bounded identity.

Run `node scripts/play/objective-workbench-check.mjs`. Evidence is written to `playtest/objective-workbench`. The runner uses real native controls, independent ECS name/shape/transform enumeration and resumed render counts after consequence publication. It checks invalid edits, isolated preview lifetime, undo/redo/reload, explicit adoption, shared-work cancellation, branch-specific outcomes, capacity failure, failed writes and acknowledgment, and independent recovery refusal.

Only the independently selected desktop keyboard/pointer profile is exercised (1440×960 Chromium). This is not phone/tablet, gamepad, physical-device performance or production multiuser certification. The reading sheet deliberately pauses the background scene while open; accepted publication closes it before claiming visible scene evidence.
